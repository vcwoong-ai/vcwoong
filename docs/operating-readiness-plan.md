# 운영 저장소 전환 준비

현재 코드는 신규 비공개 저장과 권한 다운로드를 지원하지만 운영 저장소·환경·기존 공개 원본은 이번 작업에서 확인하거나 변경하지 않았다. CI의 격리 환경 통과는 운영 적용 또는 기존 원본 비공개 전환의 증거가 아니다.

## 읽기 전용 계획 도구

`npx --no-install tsx tools/ops-readiness.ts`는 환경 파일, DB, 네트워크, 기존 파일에 접근하지 않고 미검증 체크리스트만 출력한다. 외부 의존성 설치 없이 이미 설치된 tsx를 사용한다. `--target private-blob`, `private-s3`, `private-local`로 목표를 선택하고 `--inventory <명시한 JSON 경로>`로 승인된 메타데이터 목록을 전달할 수 있다. JSON은 배열이며 각 항목은 `recordId`, `kind`, `storageRef`, 선택적 `size`를 가진다. `kind`는 `vc-document`, `pe-document`, `template`, `extracted-image` 중 하나다.

입력에는 원문·문서명·회사명·API 키를 넣지 않는다. URL에 인증값을 넣지 않는다. 입력 원본은 운영자가 제한된 위치에서 보관하고 Git·공유 메모리에 저장하지 않는다. 도구 출력에는 원본 ID·URL 대신 안정적인 SHA-256 참조가 포함된다. hash는 작업 항목 연결용이며 익명화 보장은 아니다. 동일 항목은 제거하고 정렬하므로 같은 목록을 다시 입력하면 같은 계획을 얻는다. `private` 분류는 URL 형식에 대한 판단이며 실제 접근 정책을 검증한 결과가 아니다.

도구에는 복사·삭제·DB 갱신·스토리지 접속 기능이 없다. 기본 실행과 합성 입력 검증만 로컬에서 가능하며 실제 운영 inventory 조회는 별도 승인된 읽기 전용 작업이다.

## 신규 저장소 설정과 확인

1. **Blob:** 비운영 private access store를 준비한다. 운영자만 서버의 토큰·store ID를 설정하고 실제 store 정책을 확인한 다음 `BLOB_STORE_ACCESS=private`를 선언한다. 이 환경 선언만으로 기존 public store가 변경되지는 않는다. 키 값은 로그·문서·브라우저에 전달하지 않는다. 새 토큰 또는 환경 변경은 별도 작업으로 승인받는다.
2. **S3:** 전용 비운영 버킷, Block Public Access, 공개 버킷 정책 제거, 필요한 서버 역할의 최소 `GetObject/PutObject/DeleteObject` 범위를 확인한다. 코드의 ACL 생략만으로 버킷을 비공개로 만들 수 없다. 실제 운영 정책 변경은 승인 후 수행한다.
3. **연동:** 합성 문서로 업로드·파싱·원본 다운로드·추출 이미지 포함 PPTX를 검사한다. 로그아웃/타팀은 거부되고 소유자/같은팀은 허용되며 응답은 attachment와 private/no-store여야 한다. Blob 직접 원본 요청은 인증 없이 거부되고 잘못된 host/path·redirect·파일 크기 제한을 검사한다. 과금 API나 실문서로 시험하지 않는다.
4. **DB:** `docs/schema-readiness.md`의 명시적 조회 전용 DB 선택 절차로 대상 schema를 확인한다. 누락 객체는 별도 적용 계획을 만들며 migration/DDL은 자동 실행하지 않는다.

## 기존 public 원본 전환

승인된 조회 담당자가 VC Document.url, PE MADocument.url, Template.fileUrl, Document.metadata.images의 모든 참조를 수집한다. URL이 같은 객체를 여러 레코드·추출 이미지가 참조할 수 있으므로 객체 단위 및 레코드 단위 목록을 함께 유지한다. 운영 대상 branch/schema/store·코드 revision·원본 개수·바이트 합계만 안전하게 보고하고 URL 목록은 제한된 migration journal에서 관리한다.

별도 승인된 실행자는 다음 순서로 처리한다.

1. **복사:** 원본을 읽고 새 private target에 복사한다. 원본은 유지한다. 목적지는 migration run ID와 opaque object ID로 결정하고 덮어쓰지 않는다. 기존 목적지가 있으면 checksum을 비교하고 일치할 때만 재사용한다.
2. **검증:** 읽은 바이트 수와 SHA-256을 복사본과 비교하고 서버의 private 읽기가 되는지 검사한다. 원본과 복사본의 값·상태를 보호된 journal에 저장한다. byte 내용·키를 로그에 쓰지 않는다. 검증 실패 항목은 전환하지 않는다.
3. **참조 전환:** `현재 값 = inventory에서 조회한 이전 참조` 조건으로 관련 레코드 및 이미지 참조를 갱신한다. 값이 달라졌다면 충돌로 보고 재조회한다. 지원되는 관련 레코드는 transaction으로 처리한다. 동일 계획 재실행 시 이미 전환된 checksum 일치 대상은 건너뛴다.
4. **권한 확인:** 새 원본으로 인증 다운로드와 PPTX가 동작하고 타팀·익명이 거부되는지 확인한다. DB·객체 개수, 미전환 참조, 파일 무결성, 실패 목록을 대조한다. 다른 store의 기존 원본은 현재 자체 host 제한에서 읽히지 않을 수 있으므로 전환 창과 호환 전략을 먼저 확정한다.
5. **공개 원본 삭제:** 앞 단계 검증과 운영자의 별도 삭제 승인을 받은 뒤 수행한다. 승인된 보존 기간과 backup 정책을 따르고 모든 참조가 전환됐는지 다시 검사한다. 공개 URL 폐기 전에는 기존 파일 보호 완료로 보고하지 않는다. CDN cache 폐기·TTL도 확인한다.

## 롤백과 중단 조건

공개 원본을 삭제하기 전에는 journal의 이전 참조로 compare-and-swap 복구할 수 있다. 다만 public 참조 복구는 다시 공개 노출을 허용하는 행동이므로 그 위험과 대안을 승인받고 시행한다. 비공개 복사본은 복구·보존 기간이 끝나기 전 삭제하지 않는다. 공개 원본 삭제 이후에는 backup에서 복구해야 하며, 삭제 승인은 이 복구 한계를 포함해야 한다.

checksum 불일치, 대상 접근 정책 미확인, schema drift, 외부 store, 권한 실패, 예상하지 못한 레코드 변경이 발생하면 해당 항목을 중단한다. 전체 과거 SQL 실행, 자동 `db push`, 전체 bucket 삭제를 복구 방법으로 사용하지 않는다.

이번 도구 실행 권한은 계획 작성 범위다. 실제 키·환경·bucket/store 변경, 운영 원본 복사/삭제, DB 참조 수정, 배포는 각각 검토 가능한 대상 목록·검증 결과·롤백 계획을 준비한 뒤 별도 승인받는다.
