# 결제 보류 확인·복구 준비 절차

작성일: 2026-10-05. 이 문서는 현 소스에 근거한 운영 준비 절차다. 운영 DB·Toss 조회, 결제·환불, 키 발급·교체, 데이터 변경, 배포 또는 활성화를 수행한 기록이 아니다. 현재 `src/lib/payments/checkout-readiness.ts:8`의 준비 gate는 `false`다. 이 문서로 gate를 해제하지 않는다.

## 1. 원칙과 승인 경계

- 먼저 원장을 읽어 사건을 분류한다. 화면 오류나 고객의 결제 완료 알림만으로 결제 성공·실패를 단정하지 않는다.
- `UNKNOWN`은 기존에 저장한 **같은 주문**을 조회해 확인한다. 주문번호·멱등키·기간·금액을 새로 만들지 않는다. 조회 결과가 없거나 조회에 실패해도 새 청구가 허용되지 않는다.
- `ISSUING` 또는 발급 `HOLD`는 `authKey` 재발급·재사용으로 자동 해제하지 않는다. 키 발급의 불확실한 결과에 청구 API의 멱등성을 그대로 적용할 수 있다고 가정하지 않는다.
- 보류 상태를 DB에서 `PREPARED`로 되돌리거나 `firstChargeAt`, lease, version, 원장 행을 삭제하지 않는다. 새로운 자동 해제·강제 재청구 기능은 현재 제공하지 않는다.
- 읽기 전용 진단과 조정은 별도 단계다. 실제 운영 조회도 대상 상점·DB·기간·담당자·승인 범위를 명시한 후 진행한다. provider 조회, 관리자 조정, 결제·환불·원장 변경은 각각 해당 작업을 승인받아야 한다.
- 원본 `billingKey`, `authKey`, 토큰, 비밀번호, provider secret, 암호화 키·암호문, DB URL, 고객 이름·이메일·전체 webhook 본문을 로그·공유 메모리·이슈·진단 파일에 기록하지 않는다. 해시로 만든 불투명 사건 참조도 접근 통제와 보관 기한이 필요하다.
- 복구 검토 자료에는 상태·버전·기간 인덱스·시각·금액·통화·일치 여부와 불투명 참조만 남긴다. 실제 주문/결제 참조가 provider 운영 확인에 필요하면 승인된 제한된 화면 안에서만 다루고 일반 출력에 내보내지 않는다.

## 2. 상태별 해석과 허용되는 다음 단계

동일한 `HOLD` 이름이 발급 세션과 청구 intent에 있으므로 모델을 구분한다.

| 상태/모델 | 현 코드에서 의미하는 일 | 준비·확인 절차 | 금지되는 지름길 |
| --- | --- | --- | --- |
| CheckoutSession `ISSUING` | provider 키 발급 전 DB에 작업 소유자·lease·authKey 해시가 저장됨 | lease가 살아 있으면 기다린다. 만료되었어도 provider 발급 여부는 미확정이다. 세션·method·intent 연결 존재 여부를 읽기 전용으로 조사한다 | 같은 authKey로 재발급, 새 세션으로 우회 |
| CheckoutSession `HOLD` | 키 발급·암호화·연결 중 불확실성 또는 경쟁이 있음 | provider 측 발급 증거와 로컬 저장 상태를 별도 승인 아래 대조한다. 현재 자동 복구 endpoint는 없으므로 조사·결정만 준비한다 | 고객에게 카드 인증을 반복 요청하거나 상태를 강제 READY로 변경 |
| Intent `PROCESSING` | 원격 청구 전에 최초 시도와 lease가 영속화됨 | 유효 lease에는 끼어들지 않는다. 만료 후에는 기존 주문 조회만으로 조정한다 | 다른 worker/주문으로 청구, firstChargeAt 제거 |
| Intent `UNKNOWN` | timeout, 원격 성공 뒤 DB 실패, 조회 불확실 등의 결과 미확정 | 같은 주문에 대한 인증된 provider 조회와 원장 일치를 확인한다. 정상 코드의 reconcile 경로만 사용하도록 향후 운영 실행을 승인한다 | 조회 404를 결제 실패로 확정하고 다시 청구 |
| Intent `HOLD` | 취소·금액/통화/주문 불일치·구독 정책 변경 등 검토 필요 | 영수증과 현재 기간을 분리해 조사하고 수동 조정 계획을 작성한다 | HOLD를 PREPARED로 되돌리기, 같은 회차 새 intent |
| Payment `POLICY_HOLD` | 결제 증거는 있으나 현재 권한에 적용하지 못했거나 검증된 취소가 있음 | 실제 provider 결과·사용자 소유권·현재 결제 기간·이미 지급된 권한을 대조한다 | 영수증 삭제, 부분취소를 임의 금액의 새 청구로 보충 |

근거: `src/lib/payments/checkout-session.ts:95`의 만료된 발급 작업 보류 및 `:110`의 발급 전 claim, `src/lib/payments/billing-lifecycle.ts:128`의 실행 분기와 `:135`의 조회/청구 구분, `src/lib/payments/prisma-billing-repository.ts:152`의 최초 청구 전 claim·`:161`의 조정 상태 제한. lease 만료는 provider 실패 증거가 아니다.

## 3. 사건 확인 순서

1. **안전한 접수:** 내부 사건 참조와 접수 시각만 만든다. 고객이 보낸 카드 정보·키·URL query를 그대로 기록하지 않는다. 고객에게 추가 결제를 중단하도록 안내한다.
2. **조회 범위 승인:** 운영 데이터 접근 담당자가 환경·상점·DB·조회 기간·대상 범위·최대 행수·읽기 전용 권한을 확인한다. 이 문서에 실행 가능한 운영 접속 명령이나 자격증명을 넣지 않는다.
3. **로컬 연결 확인:** CheckoutSession → method 존재 여부 → intent → payment → subscription 관계를 확인한다. raw key를 선택하지 않는다. 사용자/주문/기간/금액/통화·버전의 일치 여부만 제한된 조사 자료에 기록한다. legacy User 구독과 신규 BillingSubscription을 혼합해 추정 이전하지 않는다.
4. **진행 중 작업 확인:** 현재 lease, worker version, 최초 청구 시각, 최신 snapshot을 확인한다. 살아 있는 작업과 동시에 운영 변경을 하지 않는다. 상태를 먼저 고친 뒤 원격 결과를 확인하는 순서를 사용하지 않는다.
5. **provider 조회 승인과 증거 확인:** 승인된 운영자가 저장된 같은 주문을 조회한다. remote 결과의 주문·paymentKey·금액·통화와 해당 사용자 원장을 모두 대조한다. 원격 응답 전문은 일반 로그에 저장하지 않는다. 상점이 다르거나 결과가 불명확하면 보류를 유지한다.
6. **현재 기간 판정:** 영수증이 어느 `periodIndex`에 대응하는지, 지금 구독의 anchor·paidThroughIndex·periodStart/end·version과 일치하는지 확인한다. 과거 결제 취소와 현재 권한 처리를 분리한다.
7. **조정 계획 승인:** 원격 지급 상태, 회계/환불 정책, 고객 권한, 영향 행, 기대 version, rollback 방안, 검증 방법을 한 문서로 정리한다. 현재 일반 관리자가 임의로 보류를 해제할 수 있는 UI/API는 없으며 이 문서도 쓰기 절차를 대신하지 않는다.
8. **별도 구현·검증:** 필요한 조정 기능은 기존 User → Intent → Subscription 잠금 순서, 새 snapshot CAS, 원장 보존과 운영 감사 기록을 지켜 별도 개발한다. 합성 데이터에서 검증하고 운영 실행 승인 후 진행한다. 주문/영수증 충돌은 기존 행을 덮어쓰지 않는다.

`UNKNOWN` 정상 reconcile은 실제 결제 상태를 조회하고 일치한 결과를 원장에 적용하는 쓰기 작업이다. 읽기 전용 진단을 실행했다는 사실만으로 이 조정을 승인받았다고 해석하지 않는다. core가 같은 주문 조회를 지원해도 운영 gate가 꺼져 있는 동안 고객 callback·cron이 실행 준비되었다고 안내하지 않는다.

## 4. 취소·부분취소·과거 기간

현 구현 정책은 다음과 같다. 최종 판매 약관·회계·환불 정책은 별도 확인이 필요하다.

- 현재 지급된 기간의 **전체 취소**가 provider 조회로 검증되면 영수증을 `POLICY_HOLD`로 표시하고 현재 구독 `CANCELLED`로 권한을 보류하며 갱신을 중단한다. 자동 환불 API는 호출하지 않는다.
- 현재 기간의 **부분취소**는 영수증을 `POLICY_HOLD`로 표시하고 갱신을 중단한다. 이미 지급된 기간 권한은 유지한다. 일할 계산이나 부족분 재청구를 추정하지 않는다.
- **과거 기간 취소**는 해당 영수증 검토 상태만 기록하며 새 기간 권한·갱신 예약을 변경하지 않는다. 반드시 현재 기간·anchor·subscription version fence를 확인한다.
- 부분취소 다음에 전체취소가 확인될 수 있다. 영수증이 이미 보류됐다는 이유로 전체취소의 현재 권한 보류를 생략하지 않는다. 반대로 늦은 `DONE`·부분취소 이벤트가 취소된 권한을 다시 활성화하지 않는다.
- `BILLING_DELETED` 본문만으로 키를 삭제하거나 구독을 취소하지 않는다. 현재 구현은 확인 보류로 응답하고 데이터를 변경하지 않는다.

근거: `src/lib/payments/billing-events.ts:67`의 provider 조회, `:80`의 미청구 intent 제한, `src/lib/payments/prisma-billing-repository.ts:362`의 취소 처리·`:387`의 현재 기간 정책 판단. 웹훅의 전달 ID/상태/customer 값은 결제 증거를 대신하지 않는다.

[Toss 공식 웹훅 이벤트 문서](https://docs.tosspayments.com/reference/using-api/webhook-events)를 2026-10-05 확인했다. 일반 결제 이벤트에 서명이 있다는 가정을 사용하지 않는다. 문서의 서명 검증은 payout/seller 이벤트에 해당하며, `BILLING_DELETED` 본문에는 billingKey와 reason이 있다. 기존 사용자 지정 시크릿 헤더를 Toss의 공식 전달 인증으로 안내하지 않는다. 공개 hint 경로는 저장된 주문과 인증된 조회의 일치 검증을 사용하고, 조회 남용 제한은 별도로 유지한다.

### 결제 증거가 있으나 이용권 적용 보류

“결제 요청과 서비스 이용권의 연결을 확인하고 있습니다. 추가 결제는 진행하지 말아 주세요. 확인된 결제 결과와 현재 이용 가능 범위를 안내해 드리겠습니다.”

### 부분취소 확인

“부분취소가 확인되어 다음 갱신은 중단했습니다. 현재 지급된 이용 기간은 유지됩니다. 환불 금액과 처리 내역은 별도로 확인해 안내해 드리겠습니다.”

### 전체취소 확인

“현재 이용 기간에 연결된 결제 취소가 확인되어 유료 이용권을 보류했습니다. 결제 내역과 이용 기간을 확인해 후속 안내를 드리겠습니다. 새로 결제하지 말아 주세요.”

실제로 확인하지 않은 승인·환불 완료·복구 시각을 확약하지 않는다. 위 문구는 해당 상태와 권한 조치를 확인한 경우에만 사용한다. 일반 문의 채널에서 결제키·카드번호·인증 query를 요청하지 않는다.

## 6. 이전 단계의 공정성 한계와 후속 범위

아래 내용은 메모리 cursor만 사용하던 이전 단계의 기록이다. 현재는 독립 `BillingMaintenanceState`로 두 작업 위치·우선순위·임대·전체 실패 대기를 보존한다. 실제 변경과 적용/복구 조건은 `docs/billing-maintenance-schedule-rollout.md`를 따른다. 개별 주문 대기·긴급도·실제 고객 수에 따른 지연 목표·알림 전달은 여전히 별도 검증이 필요하다. 운영 결제와 예약 작업은 활성화하지 않았다.

**확인된 제한:** `src/lib/payments/billing-maintenance.ts:15`의 조회 상한은 20, `:24`의 renewalCursor와 우선순위는 프로세스 메모리다. `src/lib/payments/prisma-billing-repository.ts:303`은 오래된 만기 순으로 후보를 읽는다. cold start마다 cursor가 초기화되고 보류·미처리 항목이 오래 남으면 후순위 사용자의 갱신이 계속 지연될 수 있다. 실제 운영 규모·지연은 이번에 측정하지 않았다.

**다음 작업의 최소 변경안(이번에 미구현):**

1. 별도 scheduler-state 레코드에 공정성 cursor/작업 종류 우선순위·version·짧은 lease를 영속화하거나, 작업별 `nextCheckAt`/마지막 검사 순서를 저장하는 방안을 비교한다. 금액·paidThroughIndex·User.updatedAt을 cursor 용도로 재사용하지 않는다.
2. 후보 선택을 `(다음 확인 시각, 고유 id)` 등의 안정된 순서로 하고, 조회 불확실 항목의 backoff와 신규 갱신 처리 예산을 분리한다. 동시 scheduler는 CAS와 claim으로 보호한다. 미처리 과거 기간을 여러 회차 청구해 따라잡지 않는다.
3. 오래된 보류 수·최장 대기·갱신 지연·제한으로 중단된 작업·오류 수만 집계해 알림을 준비한다. 고객 식별자/키/원격 본문을 지표 태그에 넣지 않는다.
4. 예상 변경 범위는 Prisma의 전용 scheduler 모델 또는 작업 스케줄 metadata, 별도 로컬 migration 계획, `prisma-billing-repository.ts`, `billing-maintenance.ts`, 합성 다중 인스턴스·재시작 회귀다. 구체적 모델/인덱스는 성능·운영 지연 목표를 합의한 뒤 선택한다. 이 문서 작업에서는 schema를 변경하지 않았다.

검증은 20개를 넘는 보류 후보와 정상 후보, 매 invocation 새 runtime, 동시 실행, 재시작, budget 종료를 포함한다. 어떤 후보도 영구적으로 굶지 않는지 확인하면서, 과거 기간 청구·중복 청구·취소 후 권한 부활이 없음을 함께 검증한다.

## 7. 읽기 전용 집계 진단 도구

현 소스: `src/lib/payments/billing-diagnostics.ts`, `tools/billing-diagnostics.ts`. 인자 없이 실행하거나 `--help`를 사용하면 안내만 출력하며 DB client를 구성하지 않는다. 안내 확인 명령은 다음과 같다. 이번 문서 작업에서는 실행하지 않았다.

```text
npx --no-install tsx tools/billing-diagnostics.ts --help
```

실제 DB 진단은 `--run-db` 명시와 전용 `BILLING_DIAGNOSTICS_DATABASE_URL` 입력이 필요하다. 이 옵션이나 변수의 존재는 운영 DB 조회 승인을 의미하지 않는다. 실제 값은 문서·터미널 기록·공유 채널에 넣지 않는다. 일반 `DATABASE_URL` fallback은 없다. 별도 승인한 대상의 읽기 전용 계정만 공급하고, 운영 실행 전에 아래 검증을 완료한다.

- 모듈은 RepeatableRead transaction에서 `SET TRANSACTION READ ONLY`를 먼저 실행하고 고정 SQL 집계만 반환한다. 시간 제한은 쿼리 10초, transaction 15초, 연결 대기 5초다. 대상이 실제 PostgreSQL client 및 최신 승인 schema인지 확인해야 한다.
- 출력은 상태별 수·생성 시각 기준 경과 구간·갱신 blocker 수다. 사용자·주문·결제·method 참조나 원본 키는 출력하지 않으므로 사건별 대조를 대신하지 않는다. blocker는 중첩 가능하고, HOLD 경과 구간은 전이 시각이 아니라 행 생성 시각이다.
- `activation: HELD`, `providerVerified: false`는 출력에서도 유지된다. 전부 0이어도 결제 활성화·provider 결과 확인·기존 고객 이전·최신 가격 동의가 완료되었다는 뜻이 아니다.
- raw exception은 출력하지 않는다. DB 실패나 형식 오류는 일반 `UNAVAILABLE`로 다루며 0건 성공으로 바꾸지 않는다. 읽기 전용 transaction은 DB 계정 자체가 읽기 전용인지 증명하지 않으므로 권한 검증을 별도 수행한다.
- **환경파일·출력 방어:** CLI는 Prisma import 전에 **Prisma 6.19.3의 확인된 생성 형식**인지 검증한다. metadata에 자체 `rootEnvPath` 필드가 존재하며 값이 null이고, `schemaEnvPath`가 없거나 null인 client만 허용한다. 일반 환경파일 경로가 있는 client, 다른 버전이나 알 수 없는 생성 형식은 거부한다. Prisma 업데이트 시 이 검증을 먼저 재검토하고 합성 회귀로 확인한다. `DEBUG`, `RUST_LOG`, `PRISMA_LOG_QUERIES`, `PRISMA_QUERY_ENGINE_LOG_LEVEL`이 켜져 있어도 거부한다. 환경파일 없는 승인된 PostgreSQL generated client와 조용한 실행 환경을 별도로 준비해야 한다. `.env` 원문을 읽거나 기존 client를 현장에서 수정해 우회하지 않는다.
- **실행 환경의 승인:** `NODE_OPTIONS` 사전 로딩 코드는 이 CLI보다 먼저 실행될 수 있다. 신뢰할 수 있는 preload 없는 전용 환경을 사용한다. client 코드의 metadata 검사는 공급망·시작 전 실행 코드 전체를 검증하지 않는다. CLI는 접속·pool 대기를 각각 5초로 제한하고 transaction 안의 UTC 설정으로 기간 집계 기준을 고정한다.

집계 SQL은 provider 조회·청구·환불·키 발급이나 보류 해제를 수행하지 않는다. 실제 데이터의 안정된 snapshot과 UTC 경계는 합성 PostgreSQL 회귀에서 별도로 검증하며, 이번 문서 검토는 정적 확인이다.

root 담당자는 격리된 합성 환경에서 실제 CLI `--run-db` 실행의 종료 코드 0을 확인했다. 이는 해당 격리 환경 검증이며 운영 DB 진단 실행·운영 권한 확인·provider 결과 검증을 의미하지 않는다.

## 8. 복구·활성화의 미확인 항목

- 실제 Toss 상점/MID·빌링 계약과 sandbox/live 동작, 웹훅 재전송·지연·순서, 실제 발급 불확실 사건 확인 방식은 미검증이다.
- 운영 DB migration, 기존 고객/legacy billingKey의 명시적 이전, 회계 증거 대조, 고객 동의와 플랜 변경/환불 약관은 미완료다. 원본 legacy 키를 진단 대상으로 자동 읽거나 추정 이전하지 않는다.
- vault secret manager 공급·회전·재암호화·복구, 암호화 키 분실/백업 복원 리허설은 미검증이다. 키 교체만으로 이전 암호문을 복호화할 수 있다고 가정하지 않는다.
- Vercel 실제 webhook 응답 시간·cron 실행 시간·배포 계약, 처리량·알림 담당자와 장애 대응 SLA는 미검증이다.
- rollback은 새 청구 활성화를 중단하고 영수증/intent/기간 기록을 보존하는 계획으로 마련한다. gate를 끄면 조회 조정도 중단될 수 있으므로 미확정 결제 사건은 별도 담당자가 추적해야 한다. 과거 앱으로 되돌렸다는 이유로 새 원장을 삭제하거나 기존 개인 구독 필드로 복사하지 않는다.
- 로컬 합성 회귀나 읽기 전용 진단 결과는 실서비스 복구 승인·운영 적용·결제 계약 확인의 증거가 아니다. 이번 문서에서는 실제 진단 CLI·provider·운영 DB를 실행하지 않았다.
