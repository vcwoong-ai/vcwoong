# 결제 유지 작업의 영속 작업 위치·임대 적용 계획

## 현재 상태와 범위

2026-10-05 코드 기준 준비 문서다. `src/lib/payments/checkout-readiness.ts`의 결제 준비 함수는 계속 `false`를 반환한다. 런타임은 이 조건을 먼저 확인하고, 유지 작업 경로도 준비되지 않으면 503을 반환한다. `vercel.json`에 이 작업의 예약 실행 등록은 없다. 이번 작업으로 운영 결제, 운영 DB 변경, 예약 실행, 알림 연결을 활성화하지 않았다.

대상 코드는 `billing-maintenance-schedule.ts`, `billing-maintenance.ts`, `prisma-billing-repository.ts`, `billing-runtime.ts`이며 모두 `src/lib/payments/` 아래에 있다. 이 변경은 금융 원장이나 결제 권한을 대신하지 않는 작업 진행 메타데이터다.

## 저장되는 상태와 실행 정책

`BillingMaintenanceState`의 고정 단일 행에 갱신·결과 조정 작업 위치, 다음 우선 탐색 종류, 작업자 토큰·만료 시각, 다음 실행 가능 시각, 연속 실패 횟수, 시작·완료 시각과 결과를 저장한다. 내부 위치 값과 토큰은 공개 응답이나 운영 로그에 출력하지 않는다.

- 임대는 180초다. 동시에 도착한 다른 작업은 `busy` 건수만 반환한다. 만료된 임대는 조건부 갱신으로 새 작업자가 가져올 수 있다.
- 실행 예산 기본값은 105초이며 메타데이터 확보 시간도 차감한다. 외부 결과 확인·결제에 필요한 기존 70초 예약 예산이 남지 않으면 후보 조회 전에 중단한다. 한 실행에서 금융 처리 시도는 최대 2개다.
- 각 종류의 조회는 ID 오름차순, 저장 위치보다 큰 ID 조건으로 최대 20개다. 건너뛴 후보도 처리 전 위치를 저장한다. 재시작·이전 위치 행 삭제에도 값 기준 탐색을 이어가며 끝에 도달하면 처음부터 다시 탐색한다.
- 두 종류의 탐색 우선순위도 저장한다. 이는 고정 앞부분만 반복하는 문제를 줄이지만, 긴급도 순서나 모든 고객의 최대 처리 대기 시간을 보장하지 않는다.
- 정상 완료, `UNKNOWN`, `HELD`는 다음 실행까지 60초를 둔다. 실패가 있는 실행은 연속 실패 횟수에 따라 60초부터 두 배씩 늘려 최대 15분을 둔다. 실패 없는 실행은 연속 실패 횟수를 초기화한다.
- 지연은 전체 작업에 적용한다. 개별 결제 건의 재시도 간격은 구현하지 않았다. 일부 실패가 정상 고객의 작업도 늦출 수 있으며, 결과 불명확한 건을 새 주문으로 다시 청구하도록 바꾸지 않는다.

## 동시 실행과 남은 한계

작업 위치 저장·최종 완료 기록은 현재 작업자 토큰과 살아 있는 임대가 모두 일치해야 한다. 만료되거나 교체된 작업자는 새 작업자의 위치·임대·지연 시간을 덮어쓰거나 해제할 수 없다. 후보 조회 후 금융 실행 직전에도 소유권을 확인한다. 원래 결제 intent의 버전·토큰·임대 검사는 계속 최종 권한이다.

소유권 확인 직후 프로세스가 멈춘 뒤 임대가 만료될 수 있다. 확인과 외부 호출을 하나의 원자적 작업으로 묶지 않았으므로, 이 스케줄러만으로 오래된 작업자의 모든 외부 호출을 차단한다고 주장하지 않는다. 이미 시작한 외부 요청도 취소하지 않는다. 외부 중복 처리 방지는 기존 주문 멱등성·intent claim·결과 조정을 함께 검증해야 한다.

임대 시각은 애플리케이션 시계에 의존한다. 실제 실행 환경의 시계 차이, 장기 중단, 다수 인스턴스 부하 및 공급자 응답은 아직 검증하지 않았다. 후보 수가 커졌을 때의 처리 지연 목표도 별도 운영 정책이 필요하다.

## 진단과 운영 대응 준비

`src/lib/payments/billing-diagnostics.ts`는 다음 지표를 집계 건수로만 제공한다. 진단 CLI 실행 전제·승인 경계는 `docs/billing-recovery-runbook.md`를 따른다. 운영 실행 권한을 이 문서가 부여하지 않는다.

| 지표 | 해석 |
| --- | --- |
| `maintenanceNeverStarted` | 시작 기록 없음. 현재 비활성·미등록 상태에서는 예상되는 값이며 장애 증거가 아니다. |
| `maintenanceLeaseExpired` | 작업자 토큰이 남아 있고 임대가 없거나 만료됨. 해당 작업의 진행 상태와 이전 실행 종료 여부를 확인한다. |
| `maintenanceCompletionDelayed` | 마지막 완료 시각 또는 첫 시작 시각으로부터 15분 경과. 의도적 중지·지연도 포함하는 조사 지표이며 SLA가 아니다. |
| `maintenanceBackoffActive` | 다음 실행 시각이 미래임. 실패 지연뿐 아니라 정상 60초 대기에도 표시된다. |

지표만으로 임대를 삭제하거나 지연을 초기화하지 않는다. 활성 작업의 종료·금융 intent의 결과를 확인하지 않은 수동 초기화는 중복 외부 요청을 늘릴 수 있다. 결과 불명확 상태는 같은 저장 주문의 결과 확인 절차를 따르고 새 주문·새 인증키 발급으로 해결하지 않는다. 고객 식별자, 작업 위치, 토큰, 결제키, 원본 공급자 오류를 진단 출력이나 고객 메시지에 포함하지 않는다. 실제 알림 전송 및 예약 실행 연결은 아직 없다.

## 적용·되돌리기 조건

1. 별도 운영 승인 후 `prisma/patches/2026-10-05-add-billing-maintenance-state.sql`과 모델을 검토한다. 패치는 메타데이터 테이블 추가만 하며 금융 데이터를 보정하거나 이관하지 않는다. `IF NOT EXISTS`는 기존 동명 테이블의 열·타입·기본값 일치를 검증하지 않는다.
2. 운영 적용 전 테이블 정의와 생성 Prisma client를 확인한다. 새 테이블이 없거나 상태가 잘못되면 작업은 실패로 닫히며 메모리 방식으로 자동 전환하지 않는다. 새 진단 쿼리도 테이블이 없으면 사용 불가로 처리한다.
3. 이전·새 작업자가 혼재하지 않도록 실행 주체를 통제하고, 준비 상태·환경·공급자 계약·원장 검증을 별도 승인한다. 준비 함수 변경이나 cron 등록을 이 문서의 자동 후속 조치로 취급하지 않는다.
4. 되돌릴 때는 실행 주체부터 중지하고 진행 중 외부 요청·원장 결과를 확인한다. 작업 상태와 금융 기록을 삭제하지 않는다. 옛 메모리 작업자로 복귀하면 재시작 위치와 전체 지연 상태가 사라진다는 영향을 평가한다. 기존 토큰을 재사용하거나 금융 CAS를 우회하지 않는다.

## 확인 결과와 다음 범위

오프라인 `tools/test-billing-maintenance-schedule.ts`는 실제 스케줄러·유지 작업 코드를 모의 저장소와 공급자 경계로 실행했다. 재시작 위치, 건너뛴 앞부분 이후 진전, 위치 행 삭제, 동시 실행, 정상 대기·실패 지연 상한, 만료·교체 작업자의 쓰기 차단, 소유권 상실 후 금융 실행 중단, 메타데이터 확보 시간의 예산 차감, 누락 저장소의 실패 처리와 공개 건수 응답을 확인했다. 집중 타입 검사·lint도 통과했다. 실제 DB나 공급자를 사용한 검증은 이 모의 테스트의 범위가 아니다.

별도 부모 작업에서 격리 PostgreSQL 스케줄러 통합과 읽기 전용 진단 통합 검증이 통과했다고 보고받았다. 운영 DB·실제 공급자·Vercel 실행 시간·계약·키 회전·기존 고객 이관·운영 되돌리기는 미검증이다.

다음 규모 확장 범위는 고객 수·대기 목표를 먼저 정한 뒤 개별 intent 지연 상태, 긴급도 정책 및 소유권 검사를 금융 claim 안에 연결할 필요를 평가하는 것이다. 최소안은 기존 금융 버전·기간·결과 조정을 보존하며 후보 선택에만 개별 다음 시도 시각을 추가하는 방식이다. 별도 스키마·혼재 배포·성능·오래된 작업자 회귀 검토가 필요하며 이번에는 구현하지 않았다.
