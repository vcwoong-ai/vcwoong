## 설정 입력 원칙

실제 값은 공급자 또는 배포 플랫폼의 비밀 설정 입력 화면에서 넣는다. 안내 문서에 값이 필요하면 `<발급받은 비밀값>` 같은 예시만 사용한다. 연결 전후에 기존 운영 설정과 데이터가 보존되는지 확인한다. 이번 자동 작업은 운영 키·권한·데이터·배포를 변경하지 않는다.

- 마지막 운영 배포 이후의 로컬 수정은 배포 전까지 고객 화면에 적용되지 않는다.

로컬 새 DB schema 동기화와 patch 재적용 검증은 운영 데이터 이전·운영 스키마 일치·복구 성공을 보장하지 않는다. 구버전 앱으로 되돌릴 때의 writer 호환성도 각 절차에서 확인해야 한다.

생성 작업 보호에는 `prisma/patches/2026-10-05-add-report-generation-lease.sql`의 nullable 작업 ID/만료 필드가 추가로 필요하다. 이 patch는 운영에서 실행하지 않았다. schema 적용과 앱 전환 전에 구버전 생성 함수가 끝났는지 확인하고 신규 생성 진입을 통제하는 전환 계획이 필요하다. 새 코드의 작업 ID 검증만으로 검증 없는 구버전 worker의 쓰기를 차단한다고 주장하지 않는다.

결제의 영속 DB 저장소, 결제 의도·체크아웃 API, 빌링키 발급 어댑터, 사용권 연결, 조정·갱신 작업, 검증된 이벤트 처리와 웹훅 실행 구성은 로컬에서 연결하고 합성 DB/공급자로 검증했다. 실제 Toss 상점·청구·웹훅 전달·운영 DB·예약 실행은 미확인으로 새 결제 차단을 유지한다. 테스트/운영 키의 형식과 모드 일치는 검사하지만 같은 MID·자동결제 계약·사용 권한은 형식으로 검증할 수 없다. 키 종류와 서비스별 MID 구분은 [Toss 공식 API 키 안내](https://docs.tosspayments.com/reference/using-api/api-keys)를 따른다.

최신 격리 검증에서는 새 무료 고객 한 명의 가입·로그인·딜·TXT 업로드·합성 보고서 생성·편집·승인·DOCX/PPTX·재접속과 비밀번호 해시 변경 후 세션 폐기를 실제 로컬 PostgreSQL/소스 API 실행기로 통과했다. 공급자 호출·토큰·UsageLog는 모두 0이었다. 실제 AI·실제 재설정 이메일·실제 Next 서버 브라우저 UI 검증은 이 결과에 포함하지 않는다.

- 팀 소유자와 팀 전용 역할을 추가하는 PostgreSQL patch는 prisma/patches/2026-10-05-add-team-owner-role.sql이다. 기존 소유자·역할을 추정해 backfill하지 않는다. 실제 운영에 적용하지 않았다. 새 앱의 팀 조회는 새 필드를 사용하므로 운영 스키마 적용·확인 없이 배포하면 안 된다.
- 세션 폐기 검증을 배포하면 이전 버전의 JWT는 재로그인이 필요하다. 배포 안내에 이 영향을 포함한다.
- src/lib/payments/checkout-readiness.ts는 새 유료 결제 진입을 보류한다. 키 입력이나 환경 플래그만으로 해제하는 기능은 없다. 로컬 실행 구성은 연결했지만 실제 공급자·복구·이전·운영 검증을 마친 뒤 별도 활성화 변경이 필요하다. 기존 유료 사용권·결제 기록·해지 경로는 이 보류 때문에 삭제하지 않는다.
# 로컬 팀 초대·검토 보호 후속 준비 (2026-10-05)

팀 초대 수락·거절·취소·7일 만료와 소유권 이전은 로컬 구현/격리 PostgreSQL 및 실제 Next 브라우저 회귀를 통과했다. 초대 알림은 앱 설정의 받은 초대에서 제공하며 외부 이메일은 보내지 않는다. 가입된 사용자만 초대할 수 있고 수락해도 개인 플랜은 유지한다. 외부 이메일 도입 시 공급자 가입·도메인 확인·발송 실패/재시도 검증이 별도로 필요하다.

운영 적용 전 `prisma/patches/2026-10-05-add-team-owner-role.sql`에 이어 `prisma/patches/2026-10-05-add-team-invitations.sql`의 schema-first 적용을 검토해야 한다. 두 patch 모두 운영에서는 실행하지 않았다. 현재 로컬 검증은 새 DB의 Prisma schema 동기화이며 기존 운영 데이터의 patch 적용·이전 리허설 완료를 뜻하지 않는다. 초대/소유자 데이터를 추정 backfill하지 않는다.

보고서 승인 요청은 검토한 본문 버전이 필요해 클라이언트와 API를 함께 배포해야 한다. 오래된 화면의 승인에는 409와 최신 내용 확인 안내를 제공한다. 자동 재생성/편집은 승인을 다시 요구하고 오래된 근거 검증을 폐기한다. 실제 AI 결과의 투자 품질은 합성 모의 회귀로 보장하지 않는다.

### 결제 저장 연결 진행(2026-10-05)

- 결제 의도/구독 기간/원장/암호화 결제수단의 로컬 저장소와 암호화 키 보관함이 구현되었고, 격리 PostgreSQL 및 합성 공급자 검사에 통과했다.
- 서버 checkout 세션·빌링키 발급 callback·새 구독의 기간 권한을 연결했다. 자동 갱신·검증된 웹훅도 이후 단계에서 로컬 연결했다. 실제 공급자·복구·정책·운영 전환이 남아 있어 결제 화면은 준비 안내를 유지한다.
- 공급자 계약과 별도로 과금/환불/세금/기간 정책, encryption key 저장·복구·회전, 기존 사용자 및 원장 보존/계정 삭제 정책을 확인해야 한다. 실제 키·운영 자료 이전은 자동 실행하지 않는다.
- 활성화 검증/복구는 같은 주문 조회, HOLD의 수동 확인, 기간·권한 일치 검사까지 필요하다. 실패했다고 새 주문으로 자동 재청구하지 않는다.

### 준비된 결제 실행 구성의 입력과 미확인 단계

앱 활성화 전 연결할 설정 이름은 아래와 같다. 모두 예시 설명이며 값은 제공하거나 생성하지 않았다.

```text
DATABASE_URL=<POSTGRESQL_CONNECTION_URL>
NEXT_PUBLIC_TOSS_CLIENT_KEY=<MATCHING_MODE_CLIENT_KEY>
TOSS_SECRET_KEY=<MATCHING_MODE_SECRET_KEY>
BILLING_VAULT_KEY=<BASE64_ENCODED_32_BYTE_SECRET>
BILLING_VAULT_KEY_ID=<NON_SECRET_VERSION_LABEL>
```

vault key는 provider 키와 별개로 비공개 보관·백업해야 하며 분실하면 저장된 결제수단을 복호화할 수 없다. 이 입력만으로 현재 hard readiness hold가 해제되지는 않는다. 앱의 키 registry는 실행 중 갱신하지 않으므로 실제 회전은 새 key version의 읽기/재암호화·검증·배포 절차를 구현한 뒤 진행해야 한다.

- 활성화 전: checkout schema 적용과 새 구독 read/권한 배포, 이미 준비된 갱신/결과 조정·웹훅의 실제 공급자 검증, 보류 복구 절차, 실제 상점 계약과 테스트를 완료한다. callback의 120초 실행 예산도 해당 배포 환경에서 지원되는지 확인한다.
- 발급 불확실 시: 같은 authKey를 다시 발급하지 않고 HOLD를 유지한다. 공급자/상점 확인 후 안전한 복구 절차가 필요하며, 설정 입력으로 해결된다고 안내하지 않는다.
- 청구 불확실 시: 같은 주문 GET 조회로만 조정한다. 다른 주문으로 자동 재청구하지 않는다. 테스트에서는 이 조회 복구가 통과했지만 실제 supplier 연결은 미확인이다.
- 공급자 요구: authKey는 일회성이고 customerKey는 추측하기 어려운 무작위 값으로 만든다. 현재 새 checkout은 해당 방식을 사용한다. [Toss 자동결제 API 레퍼런스](https://docs.tosspayments.com/reference#인증-정보authkey로-빌링키-발급)

### 갱신·이벤트 연결 후 추가 활성화 목록 (2026-10-05)

갱신/같은 주문 재조회/검증된 이벤트의 로컬 연결은 구현되었다. 기존의 “갱신·웹훅 미구현” 기록은 이전 단계 상태다. 지금도 실제 청구는 hard hold로 차단한다.

- 준비 경로 `/api/cron/billing-maintenance`: CRON_SECRET 인증, 120초 함수 선언/105초 작업 예산/최대 2건. 공급자·배포 검증 후 승인된 cron 간격을 추가한다. 이번 작업에서는 일정을 활성화하지 않았다.
- 웹훅 일반 결제 이벤트: 본문만으로 인증하지 않고 저장된 주문의 provider GET 결과를 검증한다. 기존 사용자 지정 secret header가 Toss의 공식 이벤트 서명이라고 가정하지 않는다. BILLING_DELETED는 삭제 검증이 없으므로 자동 권한 변경을 하지 않는다.
- 실제 테스트 상점에서 주문 성공·불확실 결과·부분/전체 취소·중복/늦은 재전송과 10초 응답을 확인한다. 원래 지급한 기간·유저 권한·동일 주문 조회를 대조한다. 일반 payment event 서명 지원 여부는 공식 문서 기준으로 정리했다.
- HOLD/UNKNOWN/POLICY_HOLD 확인/복구, 놓친 갱신과 가격 변경 동의, 공정성/장애 알림, 암호화 키 복구/회전, 기존 고객 이전은 단순 환경변수 입력으로 해결되지 않는다.
- 정책: 현재 전체 취소는 권한 보류, 현재 부분 취소는 갱신 중단/기존 기간 권한 유지, 과거 취소는 현재 기간 유지. 실제 환불·세금·법적 계약 정책은 별도 확정한다. 실환불 호출은 없다.

### 보류·지연 진단과 복구 준비

`npm run ops:billing-diagnostics`의 기본 실행은 연결 없이 안내만 표시한다. 명시 `--run-db`와 `BILLING_DIAGNOSTICS_DATABASE_URL`을 지정한 승인된 읽기 전용 환경에서만 DB 집계를 수행한다. 현재 코드는 Prisma 6.19.3의 환경파일 자동 읽기가 없는 generated client만 허용하며, 디버그 출력 설정과 알 수 없는 generator 형식을 거부한다. 운영 접속이나 별도 키 변경은 이번 자동 작업에서 하지 않았다.

상태별 확인·고객 안내·조정 승인·환불 권한·미확인 운영 복구 항목은 `docs/billing-recovery-runbook.md`에 모았다. 진단은 건수와 생성 시각 기준 대기 구간을 보여주며, 개별 고객 사건 해결·실제 provider 결과·현재 catalog 가격·최소권한 DB 역할 검증을 대신하지 않는다. 보류의 자동 해제나 새 주문 재청구 기능은 없다.

### 재시작 이후 갱신 공정성과 실행 지연 준비

`BillingMaintenanceState`의 두 작업 위치·다음 순서·180초 실행 임대·정상 60초 대기·전체 오류의 최대 15분 대기를 로컬 구현했다. 실제 격리 PostgreSQL에서 매번 새 객체를 구성해 각 목록의 24개 후보 순회, 동시 실행 차단, 만료 작업의 상태 덮어쓰기 거부, 예산 중단 후 이어가기를 확인했다. 결제 lifecycle을 사용하는 합성 공급자 갱신도 중복 없이 통과했다. 실제 공급자 응답·Vercel 시간 예산·운영 규모를 확인한 결과가 아니다.

진단은 미시작·만료 임대·15분 이상 완료 지연·현재 대기의 건수만 추가한다. 결제를 활성화하지 않았으면 미시작은 정상일 수 있으며 15분은 계약한 SLA가 아니다. 정상 대기도 현재 대기 지표에 포함된다. 실제 알림 채널 전달·예약 간격은 아직 연결하지 않았다.

연결 전에 additive patch/client/app 일치, 실행 주체 단일화, 기존·신규 writer 혼재 방지, 실제 공급자/복구/가격·환불 정책, 키 보관·고객 이전을 확인한다. `docs/billing-maintenance-schedule-rollout.md`에 준비/중단/rollback 조건을 모았다. 전용 상태 추가만으로 결제 활성화 보류가 풀리지 않는다. 개별 주문 backoff와 긴급순 처리를 구현했다고 주장하지 않으며, 전체 장애 대기는 정상 후보도 늦출 수 있다.
## PE 자료 저장 연결 범위 (2026-10-05)

작은 PE 파일(4MiB 이하)은 기존 비공개 저장 설정을 사용하는 별도 PE 업로드 경로로 로컬 연결했다. 합성 로컬 저장·보호 다운로드·원문 추출/재접속·권한·중복 보호를 검증했다. 실제 Blob/S3 정책·운영 업로드·큰 자료는 미확인이다. 저장소 불확정 결과와 파서 중단은 자동 조정되지 않으며 단순 환경변수 입력만으로 복구/대용량 지원이 완성되지 않는다. `pe-document-upload.md`의 제한과 확인 절차를 따른다. 기존 공개 파일 이전·정책 검증·운영 적용은 별도 승인 범위로 유지한다.

후속 로컬 변경에서 확정된 원본의 WARNING/만료 PARSING에 대한 수동 재추출을 추가했다. 서버 편집 권한, 원본 경로/속성/바이트 해시, 원본 읽기4MiB, 새 lease/CAS, 문서당 최대3회를 적용했다. 원본 쓰기/삭제 없이 실제 격리 PG와 모바일 TXT 복구를 확인했다. 클라우드 정책·고객 원본/스캔 품질·압축 해제 CPU/메모리 격리·대용량·UNKNOWN 저장 조정은 별도 검증/구현이 남는다. 재시도 횟수 JSON 필드는 schema patch를 요구하지 않지만 새 서버 코드의 운영 적용은 아직 하지 않았다. 자세한 결과와 한계는 `autonomous-progress.md`를 따른다.

## 재설정 링크 활성화 전 확인 (2026-10-05)

토큰 소비/비밀번호 변경과 토큰 교체 발급은 로컬 원자 처리·실제 격리 PG 경합/rollback을 검증했다. 새 VerificationToken schema는 추가하지 않았다. 운영 적용 전 구버전 발급 writer를 함께 남기지 않도록 인스턴스 전환을 확인하고, 실제 발신 도메인/메일 전달/만료·재사용 거부/비밀번호 변경 후 세션 회수를 합성 계정으로 검증한다. 연속 발급의 이전 링크는 무효화되지만 이메일 도착 순서와 유효 링크 순서는 다를 수 있다. 이번 자동 작업에서 실메일이나 운영 인스턴스 전환은 실행하지 않았다.
